# providers 回退链：按失败计数循环切换的有序链

> **状态：已决定（本轮实现范围内）。** 本文把 04 §4.3.3 / 05 §5.6.4 原有的
> 「主 + 单备、批内粘滞」回退模型替换为**有序回退链**；公共规范在实现同批 commit 内同步。

## 1. 决定

供应商路由从 `primary + secondary` 二元组改为**有序链** `providers.routing.chain`
（`chain[0]` 为主，后继为备用，上限 8 项）。`internal/ai` 的 `WithFallback`（单备、一次性
粘滞 bool）废弃，替换为 `Chain`：

- 每个条目 = `{providerID, Provider}`，`Provider` 已预包 `WithRetry`（每供应商最多 3 次尝试、
  指数退避，既有策略不变）。
- 链状态**仅存内存**，按 provider ID 记连续失败数；不持久化，重启清零。
- 阈值为 Go 常量 `DefaultChainThreshold = 3`（不做设置项，避免调参 UI）。

一次 `Generate` 的语义：

1. 从 cursor（初始 `chain[0]`）出发，**环形**遍历（下标 mod n），一轮最多 n 个条目各试一次。
2. 单条目返回错误（其内部重试已耗尽）→ `failures[id]++`；本回合继续试链上下一个条目。
   连续失败数达到阈值 → cursor 粘滞前移到下一存活条目（降级），直到该条目某次成功。
3. 条目成功 → `failures[id] = 0`、cursor 指向它、立即返回。被降级的条目仍处于环上，
   每轮尾部仍会被尝试——恢复后经此规则自愈（**循环往复**）。
4. 整体 `context` 取消不计入失败（用户取消不是供应商故障）。
5. 一轮全部失败 → 返回最后一个错误。
6. 不可重试错误（auth、invalid_request）同样计数并前进——密钥失效的供应商正是回退的
   存在意义；真正畸形的请求会在一轮后原样浮出。

链在每次使用前用当前配置 `Rebuild`：按 ID 保留失败计数，被删除的供应商丢弃其计数。
会话内编辑路由不打断在途回合。

## 2. 候选与取舍

### 2.1 选中：连续失败计数 + 环形粘滞降级

**优点。** 「失败次数超过限制时切换下一个，循环往复」是明确的产品需求；计数器给出
明确的切换时机，环形遍历保证降级项可达、可自愈；状态内存态，无持久化与恢复问题。

### 2.2 未选中：保留单备粘滞模型

**淘汰原因。** 单备不满足多备用需求；一次性 bool 永不回切，主供应商恢复后仍永久走备，
与需求相悖。

### 2.3 未选中：按时间窗或健康探测自动回切

**淘汰原因。** 需要后台探测 goroutine 与时间窗状态，复杂度明显更高；环形遍历 + 成功
提升已给出等价的回切效果，且不产生额外网络请求。

## 3. 边界与已知空白

- 阈值内（未达 3 次）的失败在**本回合**仍会触发向下一供应商的尝试——降级影响的是后续
  回合的起始点。回合内即时切换与跨回合粘滞是两层不同的机制，都保留。
- `llm_calls` 诊断表（逐 attempt 记录）仍未实现，本轮回退行为没有观测表；落表时按
  provider ID 与 attempt 序号补充，见 09 §9.8 #15。
- 单供应商（链长 1）退化为「只重试不回退」，行为与旧模型一致。

## 4. 回退

若循环降级在实践中造成抖动（如两个供应商交替半故障），收紧点在 `Chain` 内部：把
「一轮全败返回最后错误」改为「一轮全败且 cursor 未推进过则直接失败」，或将阈值改为
per-provider 设置。接口 `ChainEntry` / `Generate` 不变。
