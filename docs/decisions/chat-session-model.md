## 2. 候选与取舍

### 2.1 会话模型：多会话 vs 单一滚动会话

**选中多会话。** 用户需求明确要历史记录；聊天产品心智里「多个对话、可切换、可删除」是
默认形态。代价是需要会话管理 UI 与 `chat_conversations` 表——03 §3.3.4 本就规划了它，
不是新增表。滚动会话省下的东西（一张表、一个 UI）不足以抵消体验差异。

### 2.2 provider 路由：会话级 vs 复用全局路由

**选中会话级选择，默认跟随全局链。** 不同会话用不同模型（快速模型日常问答、强模型深度
复盘）是真实诉求；实现上只是 conversation 行多一列 + 头部一个下拉，复用全局路由则要
为「换个模型问」强制用户去改全局设置。分析流水线不受影响——它仍走全局链。

### 2.3 流式：保持原子消息 vs token 增量

**选中原子消息。** 三协议流式能力不一（05 §5.12 待定表已注明），增量事件还需要带 `seq`
的重建协议；纯对话切片先把闭环跑通，等待感用「发送中可取消」缓解。token 流式保留为
后续候选，不因本文关闭。

## 3. 边界与已知空白

- 会话指定 provider 后该 provider 被删除：绑定层校验 id 存在性，删除供应商时将其从所有
  会话的 `provider_id` 清空（回落全局链）。
- 同一会话同时只允许一个在途回合（`invalid_argument`）；不同会话可并行。
- 消息内容上限 32 KiB / 条，防内存放大。
- `llm_calls` purpose=`chat` 的审计行未落（#15），本切片聊天调用无诊断记录。

## 4. 回退

会话级 provider 选择存于 `provider_id` 一列，清空该列即回到全局路由；多会话表结构即使
回到单会话形态也可继续使用（单会话 = 表里只有一行），无 schema 回退问题。
