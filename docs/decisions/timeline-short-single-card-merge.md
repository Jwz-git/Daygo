# timeline 单卡短卡恢复性融合：把孤立几分钟短卡并回前驱

> **状态：已决定（本轮实现范围内）。** 本文记录 04 §4.3.1 新增的「单卡输出短卡恢复性融合」
> 闸门；设计规格（04 §4.3.1 / §4.3.4）在实现同批 commit 内同步。

## 1. 背景

卡片校验（`internal/analysis/validator.go`）沿用 Dayflow 的规则：改写窗口内每张卡 15–60 分钟，
**只有承载窗口末端的那张卡可以短于 15 分钟**（`i < len(spans)-1` 豁免）。这条豁免对多卡窗口
是对的——证据到窗口末端为止，末段留给下一轮滑窗。

但一个批次只生成**一张**卡时，那张卡永远同时是首卡与末卡，**下限对它从不生效**。于是
「切换任务只做了几分钟」这类活动（例如在一段编码后回了 5 分钟消息就离开）会以一张几分钟的
短卡落库，而滑窗下一轮不会回头收拾它——它已在自己的窗口里终态。用户看到的就是时间线上
时不时冒出的一张读不出多少内容的短卡。

## 2. 决定

在 `generateCards` 之后、`ReplaceCardsInRange` 之前补一道**确定性**闸门
（`mergeableSingleCardPredecessor` + `buildMergedShell`，`internal/analysis/service.go`）：

当本批次输出**恰好一张卡 C 且 `C.end − C.start < 10 分钟`** 时，寻找紧邻的已提交前驱卡 P
（`existing` 中结束时间 `≤ C.start` 的最近一张）。满足以下全部条件则把 C 并入 P：

- `P` 不是 `Idle` 也不是 `System`；
- 邻接：`C.start − P.end ≤ 4 分钟`（且不为负）；
- 融合后跨度：`C.end − P.start ≤ 60 分钟`（复用 `maxCardDuration`）。

融合卡：

- **身份取占多数时间的活动**（`buildMergedShell`）——`P` 的时长 `≥` `C` 的时长时归 `P`
  的分类 / 标题 / 摘要，反之归 `C`。间隔属于谁都不算。
- 跨度取 `[P.start, C.end]`；
- `activityPoints` 与 `distractions` 两卡按序合并（前驱在前）；
- `appSites` 以多数方为先，其为空时回退到另一方（避免融合后丢图标）。
- `ownedFrom` 前移到 `P.start`，改写因而拥有并软删除 `P`——否则
  [03 §3.5](../03-data-model.md#35-时钟串派生) 的所有权校验会拒绝一次未覆盖整卡的改写。

任一条件不满足则不融合，短卡照原样落库。

## 3. 候选与取舍

### 3.1 选中：确定性后处理闸门，跨分类按多数时间归属

**优点。** 时机明确（只在单卡短卡这一确定场景触发），不引入额外 LLM 调用与不确定性；
参数（10 / 4 / 60 分钟）是显式常量，行为可用纯函数夹具钉死。跨分类允许是有意的：孤立短卡
恢复的价值在于消除碎片，而多数时间分类规则把归属交给占时间更长的一方，日 / 周占比的偏差
被限制在少数分钟内。

**代价。** 跨分类融合会把少数分钟记到另一分类名下，日 / 周占比因此有几分钟的偏移。这是
本决定明确接受的取舍：与其保留一张读不出内容的短卡，不如用少数分钟的分类归属换回一张
可读的卡。

### 3.2 放弃：让模型在下一轮把短卡并进来

滑窗下一轮并不拥有已终态的短卡窗口，模型看不到「该把它并掉」的信号；即便看到，也是把
确定性的边界判断交给不确定的生成，与 §4.3.4「融合有确定性闸门，不依赖模型自律」相悖。

### 3.3 放弃：放宽 15 分钟下限对单卡的豁免

直接不豁免单卡会逼模型把一段真实的短窗口硬拉到 15 分钟，或反复校正失败——豁免本身是对的
（证据到窗口末端为止），问题只在于**没有可并入的邻居时**短卡无处可去。融合而非拉长才对症。

### 3.4 放弃：无条件跨分类吞并（复用 §4.3.4 的模型声明融合）

§4.3.4 的 `mergeOwnershipStart` **拒绝**模型声明的跨分类吞并，正是为了保护日 / 周占比。本闸门
不改动那条规则：它是生成完成后的独立步骤，只在单卡短卡场景触发，且用多数时间分类约束归属，
因此与 §4.3.4 并存而不冲突——模型自己声明的跨分类吞并仍被拒绝。

## 4. 与既有约束的关系

- **单卡模式的前提**：`cardRewriteStart` 只有在五分钟持续窗口内没有任何前驱卡时才进入
  fresh 单卡模式。因此一张**真正孤立**的新卡，其与最近前驱的间隔必然大于 4 分钟，通不过
  邻接闸门而独立存活。本闸门实际救回的是**紧跟一张跨分类邻居**的短卡（前驱在五分钟内、
  但因跨分类被 `mergeOwnershipStart` 拒绝合并的场景）。
- **所有权校验**（03 §3.5）：`ownedFrom = P.start` 保证改写覆盖并软删除整张 `P`，不会触发
  「改写未覆盖整卡」的拒绝。
- **`notifyDays`** 相应从 `P.start` 起算，让前移后的改写正确刷新受影响的逻辑日。

## 5. 验证

- 纯函数夹具（`internal/analysis/merge_short_card_test.go`）：`mergeableSingleCardPredecessor`
  的每条边界（≥10 分钟不融合、无前驱、Idle / System 前驱、间隔 >4 分钟、跨度 >60 分钟、
  邻接跨分类融合、末尾更晚的卡不算前驱），以及 `buildMergedShell` 的多数时间归属与
  metadata 合并 / `appSites` 回退。
- 端到端（`internal/analysis/pipeline_test.go`）：一张紧邻前驱的短单卡被并回前驱且取多数
  分类；一张间隔超过 4 分钟的孤立短单卡独立存活。
