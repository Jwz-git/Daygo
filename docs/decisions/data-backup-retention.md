# data 备份保留份数：7 份

> **状态：已决定（db-core / 维护实现范围内）。** 本文对应 `09 §9.8` 待定项 #10，
> 负责模块 data，截止时机为「维护任务实现前」。默认值体现在
> `storage.DefaultBackupRetention`。

## 1. 决定

每日备份保留最近 **7 份**（约一周回溯），超出后按最旧优先删除。

## 2. 依据

| 考虑 | 说明 |
|---|---|
| 覆盖真实故障窗口 | 能在事后几天内察觉的问题（误删、迁移引入的静默错误）最需要回溯；7 天覆盖一周工作周期 |
| 成本有界 | 每份是完整数据库副本。数据库以索引与文本为主，7 份的总量远小于同期的录制文件占用 |
| 与清理的交互 | 备份与录制共用同一磁盘上限意识；备份数量固定，不会随使用时长无界增长 |
| 可调 | 作为默认值而非硬编码常量：调用方可传入更小的 `retain` |

## 3. 候选与取舍

### 3.1 选中：7 份

一周回溯，一次典型的「周一发现问题、上周末引入」可以覆盖。

### 3.2 未选中：3 份

磁盘占用最小，但只能回溯三天。一个跨周末引入的问题在周一发现时已经无备份可用，
恰好落在最需要备份的场景之外。

### 3.3 未选中：30 份

回溯一个月，代价是磁盘占用明显上升（每份完整副本）。在 v1 数据量下收益不足以支撑
这份占用，且与 `storage.recordingsLimitBytes` 的磁盘预算存在竞争。

### 3.4 未选中：不轮换（无限保留）

**淘汰原因。** 与 U9「不会某天发现硬盘被占满」直接冲突。备份不受
`storage.recordingsLimitBytes` 约束，无界增长会绕过用户设定的磁盘上限。

## 4. 实现要点

- 备份用 `VACUUM INTO` 而非文件复制：复制活动数据库可能捕获到撕裂的 WAL，
  产出无法打开的备份。
- 备份**要求写入锁**。只读实例不生成备份，避免产出看似权威的副本。
- 轮换按文件名排序，名称内嵌可排序的 UTC 时间戳，因此字典序即时间序。
- 轮换失败不回滚已完成的备份，也不使备份整体失败：先保住刚生成的副本。
- 目标文件已存在时 `VACUUM INTO` 会失败，这是期望行为——静默覆盖会破坏备份历史。

## 5. 边界与已知空白

- **留存上限对 `llm_calls` 与卡片不适用**，那是 `09 §9.8` 的 #15，仍未决定。
- **备份不加密。** 数据库不含密钥（密钥在钥匙串），但含时间线内容。
  本地文件权限沿用目录 `0700`，与 `07 §7.6`「卸载即彻底删除」一致。
- **恢复不是自动路径。** `RestoreFromBackup` 需显式调用，且会把原库改名为
  `.replaced` 而非删除。`docs/modules/data.md` 明确实际 schema 升级不能靠 git revert 降级，
  恢复属同一类不可逆动作，必须由人决定。

## 6. 回退

保留份数只是 `MaintainerOptions.BackupRetention` 的一个值。调整它不影响既有备份文件的
可读性，也不改变轮换语义；无需迁移。
