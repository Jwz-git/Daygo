# Daygo 特色功能机会研究（2026-09-26）

> 状态：产品研究与候选建议，尚未进入交付范围。本文不代表功能已实现、已验证或已经排期。
> 依据是当前仓库与同类产品官方公开资料；未安装实测竞品、未进行用户访谈或商业需求验证。
> 实现和验收状态仍以 [09 §9.1](../09-roadmap.md#91-模块总表) 为准。

## 结论

建议把 Daygo 的特色集中在“帮助个人继续推进工作”：从时间线中恢复上次进度，把跨天活动
串成项目脉络，再让每个结论能回查依据。自动日报、更多图表、普通 Chat 和 MCP 本身已不足
以构成明显差异。特色可以来自流程完成度与可信度，不必声称行业首创。

建议先验证**工作接续卡**，以**结论来源与记录缺口**作为共同基础，再推进**跨天项目脉络**。
这三项可复用当前卡片、分析、帧回放与 Provider，首轮不需要增加录音、键盘记录、云端账号或
任意文件系统访问。是否有人持续使用、是否愿意付费，公开资料不能回答，须另做真实试用。

## 现有基础与边界

核对 [产品需求](../01-product-requirements.md)、[隐私规范](../07-privacy-security.md)、
[timeline](../modules/timeline.md)、[daily](../modules/daily.md)、[weekly](../modules/weekly.md)、
[chat](../modules/chat.md) 与 [agent](../modules/agent.md) 执行册，并抽查当前代码：

- 已有自动时间线、帧回放、卡片编辑、审阅与评分、日记与目标、日报生成、周聚合等实现。
  Chat 和 CLI / MCP 亦有部分实现；Chat v1 不交付，真实 MCP 客户端多日闭环尚未验收。
- 搜索尚未实现。搜索、导出、Chat / MCP 完善属于已有范围的补齐，不能包装成新发现的特色。
- 当前主要观察系统主显示器，采用离散截图。未观察到的其他屏幕、线下工作与采样间隙不能
  被解释为“没工作”。分析批次目标约 15 分钟，工作接续卡不能直接承诺秒级出现。
- [周统计实现](../../internal/insight/weekly_detail.go) 的 focus 是按分类与 isIdle 派生的时长，
  不是对认知专注或产出质量的测量；最长值来自单个符合条件的卡片片段。
- [日报输出](../../internal/insight/standup.go) 当前是文本条目，没有逐条来源引用字段。提示词
  要求依据记录，不等于已经保证结论无幻觉。
- [卡片改写](../../internal/storage/cards.go) 会软删重叠旧卡片并插入新卡片。长期记忆不能只绑
  一个卡片 ID；引用需要处理重分析、删除与像素到期。具体版本和锚点机制尚待设计。

继续遵守个人使用、用户配置 Provider、隐私双保护和离散截图边界。所有可见文案实现时覆盖
全部九个语言包；业务日期交由后端 timeutil 计算，不在前端推算 4 点边界。

## 同类产品说明了什么

以下只归纳官方明确介绍的能力，不把营销效果承诺当作实验结果，也不凭页面没提某项功能
就判定它不存在。资料查阅日期为 2026-09-26。

| 产品与官方来源 | 公开能力 | 对 Daygo 的启示 |
|---|---|---|
| [Dayflow 产品说明](https://www.dayflow.so/product-details/) | 时间线、日 / 周回顾、Markdown 导出、MCP / CLI，以及本地或自选 Provider 分析 | 与 Daygo 高度邻近；补齐摘要和连接能力主要提高完整度 |
| [Screenpipe 产品说明](https://screenpipe.com/about) | 本地桌面记忆、屏幕 / 应用文本与音频索引、AI 搜索 | “本地记忆 + 搜索”已是公开路线；Daygo 可选择更窄的采集边界 |
| [Screenpipe 工作上下文说明](https://screenpipe.com/integrations/codex) | 找回瞬时错误、需求上下文、恢复长会话，并形成有来源的交接材料 | 工作恢复与来源追踪也不是全新概念；机会在 Daygo 的个人使用流程 |
| [Rize 更新记录](https://rize.io/changelog/all) | 项目 / 标签、仪表盘、AI 报告、Chat / Agent、MCP，以及团队经营能力 | “AI + 时间统计”功能密集；Daygo 无需进入团队监控或经营管理 |
| [Rize 置信度说明](https://rize.io/changelog/ai-confidence-score-auto-tagging) | 标签建议显示数值置信度，并可按阈值自动应用 | 单独加一个置信度数字已有先例；未经校准的模型分数不应被当作正确概率 |
| [Timely AutoSheet 手册](https://www.timely.com/help/handbook/autosheet/timely-autosheet/) | 根据 Memory 与集成数据生成工时表草案，用户复核确认 | 工时草案已有成熟产品路径；Daygo 更适合突出个人工作的接续与理解 |

据此推断：对 Daygo 来说，差异更可能来自“用很少操作得到可靠的下一步”，而非采集更多
数据或新增一个通用对话入口。该判断是产品假设，不能据此证明市场空白或竞争优势。

## 八个候选方向

优先级是本次建议；投入为相对判断，没有进行工期估算。独立选择与用户纠错优先于自动化。

| 候选 | 用户得到什么 | 相对投入 / 主要难点 | 建议顺序 |
|---|---|---|---|
| 工作接续卡 | 被打断或隔天回来，直接知道上次停在哪里 | 中：最后状态与未完成事项容易误判 | 首轮验证 |
| 结论来源与记录缺口 | 看得见每条结论依据、尚未观察到什么 | 中：引用更新、删除、缺口归因 | 首轮基础 |
| 跨天项目脉络 | 把零散活动串成同一项目的进展 | 中高：同名项目、话题聚类、纠错 | 第二轮 |
| 决策与失败尝试记录 | 记住哪些方案试过、为何暂时放弃 | 中高：动机不能只由截图推出 | 项目脉络之后 |
| 意图与实际对照 | 看见自己计划做的事与记录之间的偏差 | 中：目标映射与记录覆盖偏差 | 第二轮可选 |
| 个人工作方式实验 | 比较自己试用的两种工作安排 | 高：样本、任务差异与因果解释 | 后续探索 |
| AI 协作成果记录 | 把多个 AI 会话与最终工作成果联系起来 | 高：采样不完整、结果归因困难 | 后续探索 |
| 选择性长期记忆 | 决定哪些已确认成果值得长期保留 | 高：派生数据、备份与出网边界 | 后续设计 |

### 1. 工作接续卡

场景：上午排查数据库锁问题，下午处理别的任务，隔天回来需要重新翻终端和聊天。
在原有卡片详情或当日入口提供一张短卡，呈现：

1. 上次记录到的工作对象与时间；
2. 当时可观察到的最后状态；
3. 尚待确认的问题或用户明确留下的下一步；
4. 对应卡片 / 帧依据。

示例均为虚构：

> 上次：排查连接锁等待。最后可见状态：测试仍出现 busy。
> 下一步草案：比较只读连接初始化顺序。依据：昨日 16:20 的记录；待你确认。

首版只在用户请求时从已经完成分析的记录生成，允许补一句“下次从这里继续”。记录不够
就显示不足，不把最后一帧当最终状态，不把模型建议当作已安排任务。不要自动执行画面里
的命令或操作外部应用。将来可以为用户自己选中的文本提供预览与复制。

新意在从“翻阅昨天”变成“接着做”。Screenpipe 已公开类似上下文恢复能力，因此不能声称
独创。适用人群是频繁中断、多项目并行的人；连续单任务工作者可能受益较小。

验收：用户可回查每个事实；跨天、部分失败、分析未完成与多项目交错时不串任务；比较
使用时间线与使用接续卡后的找回进度耗时，同时记录修正耗时和危险误导。生成得快但修正
很久应判失败。第一轮无需改捕获或原生生命周期。

### 2. 结论来源与记录缺口

让日报、接续卡、问答中的事实条目带可点击的来源，并区分“记录可见”“用户确认”与
“模型推断”。例如“排查了支付重试问题”有活动记录支撑，“问题已在生产修复”若没有
明确结果或用户确认，就不能以事实呈现。

一条来源只是支持材料，不保证解释正确；UI 不用未经校准的“97% 正确”数字代替证据。
并显示：分析仍在处理、失败批次、屏蔽时段、像素已经到期、已知暂停或睡眠等状态。
缺口原因拿不准时写“未记录 / 原因未知”，不推断用户当时离开或没有产出。

最小切片：为新生成文本增加经过校验的来源引用，不改原始卡片事实。重分析后把旧引用
标为过期或重新核查；删除与分段清理后如实呈现来源不可用，不能为了证据链阻止既有清理。
用户确认内容独立保留，不被后台生成覆盖。

验收：来源引用不存在、已经删除、时间窗不匹配时必须拒绝或降级；截图中“忽略指令”的
文字不会触发操作；模型自己增加的成果没有支持时无法进入已确认事实。属于 timeline /
daily / chat 的共同能力，需先更新接口契约，做双侧校验和真实 Provider 样本复核。

### 3. 跨天项目脉络

当前时间线主要回答“某天做了什么”。新增主题视图回答“这一件事过去两周如何推进”。
例如同一缺陷关联文档阅读、复现、失败尝试、实现、验证与用户确认的完成点，显示已记录
投入、阶段变化、开放问题和来源。不要把时长当作成果、把看过工单当作完成工单。

首版由用户选几张卡片建立主题，系统只建议归组，支持拆分、合并和别名。先解决关键词
检索，再考虑语义检索，不以一上来建全量向量库为前提。项目归属应区别于“编码 / 阅读”
这类活动分类，也不自动修改现有分类体系。

验收：同名不同项目、同项目不同名字与跨 4 点卡片不被混淆；纠错后相关视图一致；匿名
夹具和真实试用分别验证查询正确性与实际找回成本。主要归 timeline / data，由 daily /
weekly 消费，所有 schema 归 internal/storage。

### 4. 决策与失败尝试记录

为项目脉络添加可确认的检查点：“尝试了什么 → 观察到什么 → 为什么暂时放弃 → 什么
条件下值得再试”。几周后可回答“为什么当时没有用方案 A”，减少重复踩同一条路。

系统可提出候选记录，但屏幕没出现某方案不能证明它被否决；一次失败不证明方案永远
不可行。动机与决定由用户补充或确认，保留适用条件与被后续证据推翻的可能性。

首版在卡片详情增加手动检查点即可，不做全自动决策识别。验收看用户是否能找回过去的
依据，以及确认成本是否小于重建笔记的成本；不以生成了多少条为成功指标。

### 5. 意图与实际对照

复用每日意图 / 目标，让用户关联今天希望推进的主题。结束时展示计划关联记录、临时插入
事项与未观察到的部分，并允许补记线下工作。适合回答“总在忙，想推进的项目却没动”。

默认日末回顾，不做实时批评或强制网站拦截。切换应用可能是查资料，不能直接算分心；
全天录制不完整时不能对整个工作日下结论。只展示已记录投入，不输出道德化的效率分数。

验收：用户能解释偏差并选择明天的一个调整；如果要花很多时间给卡片贴目标标签，或
误报迫使用户反复自证，就应缩小自动识别范围。属于 daily / timeline，提醒默认关闭。

### 6. 个人工作方式实验

用户选择一个具体问题，例如“把沟通集中到两个时段，是否更容易完成计划任务”。先明确
比较规则，记录执行情况，展示中断次数、已记录的工作片段与用户确认的任务完成情况。

不是看某周图表后宣布因果结论。任务难度、会议量、录制覆盖与用户执行偏差都影响结果。
先提供记录与描述性比较；涉及因果主张时需要更严格的交叉安排和足够样本，不能凭 7 天
记录输出“你的最佳工作时段”或“效率提升 23%”。不做健康或心理状态诊断。

主要归 weekly / daily；此方向的算法与用户负担较高，建议在项目和目标数据稳定后再验证。

### 7. AI 协作成果记录

面向使用多个 AI 工具的知识工作者，关联某个主题下的 AI 讨论、修改、验证与最终被用户
确认的成果：哪些建议被采用、哪些尝试失败、还有哪些结论没验证。形成面向自己下一次
工作的材料，而不是统计在 AI 应用里待了几小时。

Timely 已在公开更新中介绍对 AI 会话的追踪；“记录用了 AI”本身不新鲜。
[官方更新记录](https://www.timely.com/changelog/) 支持这一点。
Daygo 可以尝试成果与验证状态的组织，但不能由应用时长计算“AI 节省时间”或 ROI。

当前离散截图并不是完整会话日志，不应伪造原句或完整提示词。首版复用可见记录和用户
补充，不读剪贴板、不登录第三方账号抓历史。外部 AI 读取历史还涉及额外的数据目的地，
不能把“本地 MCP”解释成“数据永不出网”；需明确用户选择和返回范围。

### 8. 选择性长期记忆

把保留策略从“磁盘够不够”扩展到“哪些内容值得成为长期记忆”：像素按既有完整分段
规则到期，用户确认的重要进展、决定与备注可长期保留；未经确认的推断按用户规则过期。
这是新设计方向，不能把已有软删除描述成彻底遗忘。

必须分别处理原始段、卡片、转录、日报、聊天、索引、检查点和备份。分段内混有要保留与
要删除的帧时不能承诺精确单帧擦除；如需重编码或更细粒度分段，先形成独立决策与实验。
恢复备份后的删除语义亦须设计。已发送的 Provider 数据不能靠本地按钮撤回。

可考虑在新增出网策略中提供上传前预览或审核，但需要明确等待、离线和自动生成的行为，
不能把“先发给云端再脱敏”叫隐私保护。主要归 data / recording / providers，受 G-data /
原生媒体门禁约束，投入较大，暂不作为首轮特色功能。

## 推荐的验证次序

### 第一阶段：先证明接续卡值得做

输入：人工构造并检查匿名性的中断工作样本，覆盖多项目交错、缺少结果、误导性画面、
分析失败、原始帧到期与跨 4 点。先固定每个样本允许的事实、禁止的推断与来源。

操作：先以用户主动请求、已完成分析的卡片生成接续草案；结构化输出校验、来源核查与
用户确认构成最小垂直切片。第一版不要求新增平台采集能力。

输出与完成标准：可回查、可修正的接续卡；缺乏记录时明确无法判断；原始卡片不受影响；
只读实例禁止确认写入；取消和 Provider 失败可观察；全部语言完整。以 fixture / 双侧契约 /
真实 Provider 分别验收，不因 fake 通过宣称真实功能完成。

### 第二阶段：真实个人试用

建议邀请约 5 名目标用户试用 7–14 天，这是拟议实验，尚未发生。优先选择确有多项目或
跨天中断的人，不把只看演示的喜欢当成需求验证。原始工作内容保留在参与者本机。

对可比较的接续事件交替使用普通时间线与接续卡，记录：

- 找回上次状态所需时间（包含纠错时间，注明由用户自报）；
- 事实被修正、来源不足和错误任务混合的次数；
- 无提醒情况下是否再次使用、是否确认下一步；
- 额外 Provider 调用、等待和资源成本。

可以预先设定“多数参与者重复主动使用，找回时间中位数下降约 30%，没有严重误导”作为
探索性继续条件。这些数值是待讨论的产品门槛，不是实验结果、行业基准或统计显著性保证。
若只在相似任务中有效，应明确收窄目标用户；若复核成本抵消节省时间，先改输出再扩范围。

### 第三阶段：再扩到项目脉络

只有接续需求得到真实试用支持后，再增加跨天主题、决策检查点和意图对照。把已经验证的
来源机制供日报与 Chat 使用。Chat 和 MCP 作为消费入口，避免各自建立一套记忆与检索系统。

正式进入实现前同步相关执行册和 [05 接口契约](../05-interface-contract.md)；schema 更改先写
旧库迁移夹具。任何新增捕获、媒体、通知或生命周期行为单独接受对应真机门禁，不借用
2026-09-22 的历史验收。首轮回退应能停用新入口和生成任务，保留原始卡片与用户输入。

## 暂不建议投入的方向

- 团队排行榜、经理监控、自动对外日报：与现有个人隐私和非目标冲突。
- 全量录音、键盘 / 剪贴板记录、连续录屏：采集边界与原生成本显著扩大，且部分明确不做。
- 通用万能 Agent、自动打开应用或执行屏幕里的命令：超出封闭工具面，没有必要作为特色首步。
- 只增加热力图、连续打卡、专注分数或总结模板：可改善体验，但现阶段缺乏独立差异依据。
- 凭截图评定工作质量、情绪或 AI 带来的因果收益：数据不足以支持这种精度。
