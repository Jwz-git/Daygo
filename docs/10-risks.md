# 10 风险登记

> 严重程度综合考虑影响、发生可能性，以及**风险被发现的滞后程度**。滞后是关键因子：
> 一个立刻可见的崩溃，比一个三天后才被察觉的静默丢数据要轻。

## 严重

### C-1：宿主无法承载后台 Agent

**会发生什么。** Daygo 的产品定义是"关掉窗口继续记录"。Wails v2 围绕窗口构建，关闭窗口
会结束进程，其状态栏支持也不是一等能力。如果宿主做不到无窗口常驻，产品定义就不成立。

**为什么排第一。** 这是**前提**失效，不是实现缺陷。若在 UI 大规模投入之后才发现，
项目最大的一笔投入会被搁置。

**缓解。**

- recording 限时一周的宿主探针，**早于大规模 UI 扩张**：关闭窗口后至少 10 分钟进程存活且
  真实离散捕获持续、状态栏项可用、激活策略可切换；goroutine 心跳只算前置证据（[08 §8.6.1](08-testing-strategy.md#861-l2-用例) IT-14）。
- 若最终采用进程外捕获，"无窗口时继续录制"可以与宿主生命周期解耦；进程内方案必须额外
  证明关闭窗口不会拆掉捕获。
- 后备方案按优先级：(1) `HideWindowOnClose` + 适配层拥有状态栏项；(2) Wails v3，接受
  alpha 风险；(3) 精简原生外壳负责生命周期并承载 WebView，Wails 只做绑定；(4) 换宿主。

**残余风险。** 后备 (3) 会削弱"Go Core 不依赖原生"的部分依据。真走到那一步应重新审视
[02](02-architecture.md) 和 [06](06-native-integration.md)，而不是靠惯性推进。

### C-2：静默丢失捕获

**会发生什么。** UI 显示"正在录制"，实际什么也没记。用户第二天才发现时间线缺了几小时，
而且**完全无法恢复**——那些时刻已经过去了。

这是这个产品能出的最严重故障。它比崩溃更糟，因为崩溃可见，它不可见。

**新增的暴露面。** 适配层可能终止、卡死、失去连接或陷入崩溃循环，而 Go 侧的 UI 仍在显示
它最后知道的状态。

**缓解。**

- **UI 的录制状态必须只由实际收到的状态消息推导，绝不由 Go 的意图推导。** 这是架构规则，
  不是代码审查偏好。
- 看门狗：状态为 `capturing` 但 `interval × 5` 内未收到帧，切到明显的降级态并记日志
  （`recording:warning` 事件）。
- 适配层连续三次重启失败后，显示不可关闭的持久横幅。
- 自用期间的连续性断言：除已记录的睡眠/锁屏窗口外，相邻帧间隔不超过 `interval × 3`。
- 所有停止路径（含关机）都必须收尾当前分段。

**残余风险。** 若编码器静默卡死——接受帧但不产出数据——帧到达监控发现不了。必须有写入方
状态检查，并把失败**上报给 Go**，而不是只打日志（[06 §6.4](06-native-integration.md#64-已知的工程约束) 第 5 条）。

### C-3：身份与授权不稳定

**会发生什么。** 系统把屏幕录制授权和钥匙串 ACL 绑定到代码身份。如果执行捕获的二进制
呈现的身份与用户当初授权的不同，用户会在没有预警的情况下重新收到授权提示，钥匙串里的
密钥也读不出来。

对一个隐私敏感的应用来说，自动更新后突然弹出"Daygo 想要录制您的屏幕"是一次**信任事件**，
不是小问题。

**缓解。**

- 若适配层是独立可执行文件，必须发布在主 bundle **内部**，用相同身份、相同团队 ID 和
  相同 hardened runtime 设置签名，并作为宿主的一部分公证。
- **绝不**作为独立 `.app`、`LaunchAgent` 或 `LaunchDaemon` 发布——每种都会产生不同的身份。
- Bundle identifier `io.github.jwz-git.Daygo` 一旦发布不得更改（[README §1.5](README.md#15-身份标识)）。
- delivery 在原生形态决定前协调身份探针；recording / providers 真实接入前，实机确认同签名
  升级不触发新提示。Intel 与 Apple Silicon 都要测，未覆盖的设备必须标为未验证。

**残余风险。** 系统大版本升级后偶尔会失效授权。授权缺失的处理路径必须完整实现并保留
（[04 §4.1.3](04-data-flow.md#413-授权)）。

### C-4：并发实例破坏数据

**会发生什么。** 两个 Daygo 实例同时运行并都在捕获：重复的帧覆盖、`file_size` 重复计入
导致清理过度删除、批次交错包含来自两套分段的帧。

**缓解。**

- 启动时在 `~/Library/Application Support/Daygo/capture.lock` 上取独占 `flock`，进程生命
  周期内持有。取不到锁的实例以**只读模式**启动，绑定层写方法返回 `not_capture_owner`。
- 写入锁与捕获锁分开，为未来"UI 只读 + 后台捕获"的形态留出空间。
- UI 必须显示当前由哪个实例负责捕获，避免把只读实例误当成正在录制。
- 检测：IT-13，以及定期查询"来自不同分段前缀但 `captured_at` 重叠"的行。

**残余风险。** 主目录在网络挂载卷上时 `flock` 不可靠。应检测 `~` 是否在本地存储并告警。
Windows 尚无锁实现（`lock_windows.go` 直接返回错误），后果是那里根本打不开数据库——
在 `LockFileEx` 落盘前，Windows 构建不具备本风险要求的任何保护
（[决策](decisions/data-locking.md)）。

## 高

### H-1：UI 范围失控

**会发生什么。** 时间线、每日、每周三个界面各自都能无限打磨，尤其是每周的图表。
失败模式是各模块的 UI 范围不断扩展，始终无法达到用户闭环验收。

**缓解。**

- 每个功能模块 UI 实现前书面确定交互清单、完成标准与非目标。
- 每周视图先限定为合计与分类占比；具体图表由 weekly 在实现前决定，不因风险建议预选图形
  或扩大 v1 范围。
- 设定一名有权削减范围的负责人。
- 各功能可在公共契约上并行实现核心与测试，UI 的大规模扩张仍受 G-host 限制。
  已验收 cards 即可供 daily / weekly 消费，不必等待完整 timeline 界面。

**残余风险。** 推迟的界面可能永远不做。如果那是审慎决策的结果，它是可接受的产品结果——
应把这个决定记下来，而不是任由它因资源流失自然发生。

### H-2：时钟串解析偏差

**会发生什么。** 时钟串派生涉及四条相互作用的规则（三天中取最近、跨午夜、4 点边界、
System 卡片保留）。一旦偏差，卡片被放到错误的日期——**数据看似存在却找不到**。

**缓解。** 列为行为测试优先级 1（[08 §8.3](08-testing-strategy.md#83-行为测试)），配合
五时区的属性测试，以及自用期间的断言：每张卡片的 `day` 必须等于按 4 点边界算出的值，
**特别验证 03:30–04:30 创建的卡片**。

**残余风险。** 夹具覆盖不了每个时区。属性测试能缩小缺口，不能消除。

### H-3：分段格式选型失误

**会发生什么。** 分段格式一旦落盘就有存量数据。如果选的格式不支持高效随机访问、
或者未收尾时不可恢复、或者解码依赖过重，改起来要处理历史数据迁移。

**缓解。** recording 在分段格式决策前用 [03 §3.4](03-data-model.md#34-帧与分段) 的五条要求逐一验证候选格式；
先写 `Media.ProbeSegment` 的崩溃恢复测试，再定格式。保留"分段格式版本"字段的位置，
使未来能并存两种格式而不是一次性迁移。

### H-4：LLM 输出解析脆弱

**会发生什么。** 模型会输出畸形 JSON、正文前言、围栏代码块、错误类型、多余逗号。
解析失败表现为"这段时间没有卡片"，用户看到的是数据缺失，很难归因到解析器。

**缓解。** `internal/ai/jsonrepair` 独立成包并**每见到一种畸形形态就加一个夹具**
（[08 §8.3.2](08-testing-strategy.md#832-确定性的-llm-测试)）。先使用人工构造的匿名响应夹具；
未来从 llm_calls 提取样本须验证不可逆匿名化，不提交真实活动正文。解析失败必须计入诊断指标。

## 中

### M-1：纯 Go SQLite 的 WAL 行为

`modernc.org/sqlite` 是对 C 源码的翻译，保真度通常很高，但与**其它进程**连接之间的 WAL
交互是验证最少的路径。

**缓解。** data 的 db-core 独立验收：一个写入实例 + 一个只读实例并发一小时（DB-8），
回读 PRAGMA（DB-6）。失败时记录最小匿名复现和受阻接入，调查驱动 / 连接配置并重新决策。
**不得自动切换为 cgo 驱动**：internal/storage 属于 Go Core，仍受 CGO_ENABLED=0 与 Linux
测试门禁约束。其他模块的接口、fake 与无数据库逻辑可继续推进。

### M-2：WebView 渲染帧条的性能

一天的时间线可能请求数百张缩略图；拖动帧条会以交互速率请求。在 JSON 里塞 base64 会是
灾难性的。

**缓解。** 帧走 HTTP 资源处理器，让浏览器负责流式与缓存（[05 §5.5.4](05-interface-contract.md#554-资源契约)）。
从一开始就用虚拟滚动 + `loading="lazy"`。帧条用批量 `DecodeFrames`。`internal/media` 用
有界 LRU。以"一天 200 张卡片"为基准验证 60 fps。

### M-3：打包与公证

若适配层是独立可执行文件，需要正确的嵌套代码签名、匹配的 hardened runtime 设置和谨慎的
entitlement 继承。配置错误会被 Gatekeeper 拒绝，而且**只在最终用户机器上复现**。

**缓解。** delivery 在原生形态决定前以桩适配层验证完整签名与公证可行性，不等完整更新功能。
实际产物操作需具备相应身份、设备和用户发布授权；缺失记阻塞。目标 CI 中跑
`spctl -a -vvv` 和 `codesign --verify --deep --strict`。在从未运行过开发构建的机器上测试。

### M-4：时区与 DST 偏差

所有按日期限定范围的查询都依赖 4 点边界实现正确。DST 边界、半小时偏移、历史时区变更是
最容易出问题的地方。

**缓解。** 五时区夹具 + 属性测试（[08 §8.3.1](08-testing-strategy.md#831-基于属性的测试)）；
安排一个跨越真实 DST 变更的自用时段。

### M-5：适配层崩溃循环

某个持续存在的条件——损坏的分段、缺失目录、卡死的编码器——可能让适配层一重启就崩，
形成无限循环，在看似正常的同时持续耗电。

**缓解。** 指数退避，上限 60 秒。连续三次失败后停止自动重启并显示持久横幅。崩溃报告里
带上最后 50 条边界消息。IT-10。

### M-6：LLM 成本失控

每 15 分钟一个批次，一天约 60 个批次。如果空闲判定失效或重试策略过于激进，用户账单会
显著上升，而且是**用户自己的账单**——信任损失比金额本身更严重。

**缓解。** 空闲短路是主要成本节约点，必须有夹具测试保证它不退化
（[08 §8.3](08-testing-strategy.md#83-行为测试) 优先级 4）。重试次数集中在一处配置。
诊断界面展示"今日批次数 / 调用次数 / 失败次数"，让成本可见。

## 低

### L-1：字体与视觉保真度

设计令牌与字体在 WebView 中的渲染与原生控件不同（字体微调、亚像素定位、可变轴处理）。

**缓解。** 通过 `@font-face` 加载相同字体文件，接受细微差异，重新调校间距而不是与渲染器
对抗。展示字体无 CJK 字形时按 `data-dg-lang-script` 切到系统中文字体栈。

### L-2：跨进程崩溃归因

若适配层是独立进程，崩溃可能来自任一侧，两者需要不同的符号化方式。缺上下文的适配层
崩溃报告很难行动。

**缓解。** 两侧共享相同的版本号与会话 ID 以便关联；适配层崩溃报告附带最后 50 条边界消息。

## 10.2 风险驱动的能力接入

需要始终记住的区别：

- **C-1 和 C-3 是前提风险。** recording 的 G-host 约束大规模 UI 扩张，身份与分发实验
  约束原生形态和真实数据接入；独立核心逻辑与契约工作可并行。
- **C-2 和 C-4 严重但可解。** 需要谨慎实现，缓解手段已知有效。
- **M-1 是受核心门禁约束的技术风险。** 有失败复现后重新决策，不能靠引入 cgo 绕过门禁。

按模块 / 能力记录风险，不将这些风险重新组成串行阶段。门禁的受限工作、允许工作及解除证据
见 [09 §9.4](09-roadmap.md#94-全局门禁与阻塞范围)。
